# Hue Board: end-to-end source and release audit

**Snapshot:** 2026-11-08 (America/New_York)  
**Baseline:** public `wyattowalsh/hue-board`, `main@331e92706fa7a10833c52629a16bc3b0749ce2b0`  
**Proposed update:** v5.3.0, automatic native Bridge playback with explicit foreground Live Studio  
**Scope:** local reading and simulated execution of source modules, bridge protocol, state machine, Scriptable transport, React UI, build pipeline, generated bundles, regression tests, and GitHub Actions metadata. **No physical Hue Bridge, home data, or real iOS Scriptable runtime accessed.**

## Executive verdict

The application is already more than a scene demo: it has capability-aware manual controls, conservative fixture limits, a layout/animation engine, restore journaling, a cross-WebView control protocol, native compatibility controls and mocked transport tests. The most important product defect was that ordinary Play required a hidden preference to become background-capable, while iOS suspension made the unassisted Live Studio behavior look more persistent than it was. Version 5.3 makes Play hand off to Hue Bridge by default for eligible rooms, and keeps exact foreground choreography as a separate explicit action.

**Exact Studio after locking the phone is not solved in 5.3.** The Scriptable WebView cannot guarantee arbitrary ongoing background JavaScript/network output. A separate continuously running local companion or an appropriately engineered/validated native host is necessary for exact continuous choreography. Changing UI text or subscribing to `visibilitychange` does not solve this.

## Review methodology and evidence

1. Inspected the complete repository tree and main commit via the GitHub connector; reconciled core source blobs with the local working copy using Git blob SHA checks.
2. Reviewed `src/core.js`, `src/legacy.js`, `src/hue.js`, `src/model.js`, `src/engine.js`, `src/hue-layout.js`, `src/telemetry.js`, `src/controller.js`, `src/workspace.js`, Scriptable runtime/compatibility UI, `frontend/`, bundler and release scripts, CI, and test fixtures.
3. Rebuilt the TSX/Tailwind frontend and standalone Scriptable bundle locally, and executed Node fixture tests, eight simulated timing scenarios, Playwright Chromium UI tests and React-to-controller mock integration.
4. Tested automatic scene recall, incompatible scope behavior, explicit foreground Studio, cue playback, retention after close, manual controls, and failed/ambiguous scene handoffs.
5. Inspected browser screenshots and UI state at 320, 390 and 1024 CSS pixels. No claim of full VoiceOver/iPhone validation is made.
6. Compared committed bundle release digests with fresh rebuild digests. This was previously divergent on v5.2 after PR #1; version 5.3 makes reproducibility an explicit release gate.

## Acceptance criteria for v5.3

- No Hue write on startup or preference edit; an explicit **Play** on an eligible room creates/reuses a Hue scene and obtains a Bridge dynamic-palette recall acceptance before advertising phone-free playback.
- Preset Play also uses Bridge playback automatically; unsupported All lights and devices refuse without silently changing to foreground Live.
- **Live Studio** and cue sequence remain explicit foreground-only with correct pausing/ownership; no claim that exact Studio survives iOS suspension.
- A failed/lost recall acknowledgment is marked uncertain and can be stopped/inspected without discarding snapshots.
- The new `5.3.0` Scriptable bundle must be published in an immutable GitHub commit and then match its release manifest SHA-256; this release packaging is not yet complete. Installer refers to the immutable *source commit containing that bundle* and validates bytes before backup/replace.
- Node regression, timing and modern browser fixture integration run without hidden skips. Hardware and remote CI remain separately identified as unverified until actually run.

## Release packaging status (critical)

The `feat/automatic-bridge-playback-v5-3` branch currently contains **source and tests only**. Its package version is 5.3.0, but the committed `dist/` bundle and `install/install-hue-board.js` still belong to 5.2.0. Thus **GitHub installation does not yet deliver the new behavior**, and `verify:release` / `tests/installer.test.cjs` intentionally cannot pass until a v5.3 release artifact, immutable revision and SHA-256 manifest are committed in the correct sequence. Do not merge, tag, advertise installation, or change the installer pin prematurely. A standalone locally built candidate is separately available for non-hardware testing.

The account-billing GitHub Actions pre-run failure is independent and still unresolved.

## Next engineering slices (highest value)

1. **Real-device release qualification:** validate Bridge v2 scene schema and dynamic recall across real Hue color, gradient and white-only fixtures; lock/unlock, Wi-Fi loss, restoration and competing-app interactions. Record model/firmware/OS build and measured light behavior.
2. **Controller separation:** extract pure eligibility policy + scene payload (first), then journal/recovery, then transport. Golden-file or fixture-based parity tests for each move. Do not change the writer/suspension boundary by refactoring alone.
3. **Build and TypeScript integrity:** eliminate tool-environment module fallbacks, add strict `tsc --noEmit`, lock all runtime assets with an auditable provenance trail, and check byte-identical generated assets in clean environments.
4. **Dedicated always-on host for *exact* locked-screen Studio:** an opt-in controller with lease/ownership, observed-state reconciliation, restart recovery, safe credential storage and local HTTPS. Keep mobile UI a client, not an assumed daemon. Benchmark Entertainment transport and fixture capabilities before implementation.
5. **Experience/accessibility:** simplify Play/Stop/Restore states, make uncertain state prominent but not alarming, test VoiceOver, focus, increased text sizes, low motion and foreground/background transitions on physical devices.
